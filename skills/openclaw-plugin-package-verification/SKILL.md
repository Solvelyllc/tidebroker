# OpenClaw Plugin Package Verification

Use this procedure after source tests pass and before reporting an OpenClaw plugin package as installable.

1. Run the repository's package validation command and dependency audit first. Treat compiler errors and test-runner unhandled errors as failures even when every test assertion passes. Fix the underlying async or type error, then rerun the combined validation gate; complete when build, package validation, tests, and audit all succeed without unhandled errors.
2. Create a fresh temporary directory with a nested OpenClaw state directory and config path. Keep this state separate from the live installation; complete when all three temporary paths are known.
3. Run `npm pack --pack-destination <temporary-directory> --silent`, capture its emitted archive filename, and resolve the tarball path from that output rather than reconstructing it from package name or version. Complete when that exact tarball exists under the temporary directory.
4. Install the captured archive with `openclaw plugins install npm-pack:<tarball-path> --force`, setting `OPENCLAW_STATE_DIR`, `OPENCLAW_CONFIG_PATH`, and `OPENCLAW_HOME` to the temporary paths for that command. Complete when installation reports the plugin id.
5. Run `openclaw plugins doctor` with the same isolated environment. Complete when discovery, loading, compatibility, and configuration checks pass.
6. Run `openclaw plugins inspect <plugin-id>` with the same isolated environment. Treat its reported source and install metadata as authoritative instead of assuming an extensions-directory layout; complete when the expected plugin id and version report `Status: loaded` from the packed artifact.
7. Inspect the packed or installed file list when package contents are part of the acceptance criteria. Complete when required runtime files and documentation are present and source-only or secret material is absent.
8. When the package ships an entrypoint for a separate service account, extract the captured tarball and inspect the packed entrypoint's execute bits before relying on an npm-installed copy, because installation may normalize bin modes. Make the build set the required mode and make package validation enforce it. Stage the verified package in a stable account-accessible location, inspect traversal permissions, then invoke the exact packed or deployed entrypoint directly as that account; running the file through an interpreter does not verify its executable mode. Complete when the raw artifact preserves the required mode and the runtime account directly executes the same target and invocation form the service will use.
9. When reporting live operational readiness after activation, treat `Status: loaded` as package-level evidence only. Use the installed source reported by `openclaw plugins inspect <plugin-id>`, then verify that a fresh foreground turn with trusted requester context receives the expected actor-scoped tool surface before invoking bounded non-mutating operations through that installed entrypoint. Summarize only tool availability, success, result shape, and bounded counts; keep provider content out of verification output. Complete when the expected tools are exposed to that turn and each claimed live connector path succeeds without exposing content.
10. For a credential-custody claim, inspect binding and credential metadata together. Confirm the binding references the intended active generation, superseded generations are revoked, and recent audit records contain successful connection or operation outcomes. Complete when generation, status, binding, and audit evidence agree.
11. Remove temporary validation directories and any temporary configuration copies after all evidence is recorded, then verify that they no longer exist. Complete when temporary artifacts are gone and unrelated live OpenClaw state remains untouched.
12. When reporting live Gateway state alongside package readiness, run `openclaw gateway status` instead of inferring Gateway state from a system-level service lookup. Check any separate worker service directly and include its restart count when stability is claimed. Complete when Gateway runtime and connectivity are reported, and each claimed worker is active with observed restart evidence.
13. Report source-test counts, audit result, package-validation result, doctor result, inspected id/version/status, service-account execution result when applicable, bounded live-smoke result when run, credential-custody evidence when claimed, Gateway and worker evidence when checked, and cleanup result separately. Complete when each readiness claim maps to observed output.
